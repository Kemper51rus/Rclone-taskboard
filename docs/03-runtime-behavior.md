# ⚙️ Runtime Behavior

Этот документ описывает, как в приложении создаются, ставятся в очередь, исполняются и отображаются запуски.

---

## 🧭 Источники запусков

Запуск может быть создан из трёх источников:

1. Scheduler
2. Dashboard или API
3. Filesystem watcher

---

## 👀 Event-Driven Flow

Watcher работает внутри backend и используется для реакции на изменения в файловой системе почти в реальном времени.

### Последовательность

1. Backend watcher читает список каталогов из рабочего каталога задач
2. При событии watcher передаёт payload в event-логику приложения
3. API и orchestrator сохраняют событие в историю
4. Debounce-логика отсекает шумные серии событий по каждой задаче
5. События, попавшие в `exclude patterns` или `exclude_paths` задачи, отбрасываются до постановки в очередь
6. Для совпавших backup-задач создаются отдельные запуски
7. Worker исполняет только те задачи, чьи каталоги действительно изменились

---

## 🕒 Scheduled Flow

Scheduler работает внутри web-сервиса.

### Последовательность

1. Scheduler проверяет задачи каждую минуту
2. Когда наступает нужное время, создаётся запуск
3. Запуск попадает в нужную очередь
4. Worker исполняет его шаги

---

## 🧵 Профили и очереди

| Профиль | Назначение |
| --- | --- |
| `standard` | Частые и короткие задачи |
| `heavy` | Долгие и ресурсоёмкие задачи |
| `all` | Сводный запуск всех очередей из UI |

Поведение очередей определяется секцией `queues` в рабочем каталоге:

- `allow_parallel_profiles`
- `allow_scheduler_queueing`
- `allow_event_queueing`
- `definitions` с ключами очередей, числом workers и лимитами скорости

## 💾 Runtime State

### Runtime Catalog

- `taskboard/backend/app/jobs/default_jobs.json`

### SQLite Database

- путь задаётся через `TASKBOARD_DB_PATH`
- значение по умолчанию зависит от выбранного способа развертывания
- при старте включается `journal_mode=WAL`
- для каждого соединения задаётся `busy_timeout` и `foreign_keys=ON`

В базе хранятся:

- runs
- step execution history
- events
- служебное состояние scheduler

### Профилактика базы

Taskboard оставляет SQLite локальным runtime-хранилищем, но отдаёт его состояние в API и dashboard.
В разделе `Статистика` показываются размер основного файла БД, WAL, свободные страницы, открытые fd процесса, память и uptime backend.
Пока раздел открыт, эти данные обновляются автоматически вместе с polling dashboard; ручная кнопка `Обновить всё` просто запускает тот же refresh сразу.

Для ручной профилактики доступны две операции:

- `Сбросить WAL` — выполняет checkpoint и обрезает `taskboard.db-wal`
- `Сжать базу` — выполняет `VACUUM`, затем checkpoint и сохраняет время операции в `kv_state`

`VACUUM` перепаковывает файл базы. Его лучше запускать в спокойный момент, когда нет активных `copy/sync` задач.

## 📅 Выборочный обход каталогов

`job.directory_scan` ограничивает `rclone copy` датированными ветками без предварительного чтения исходного дерева. Маска раскрывается по календарным датам в заданном часовом поясе непосредственно перед выполнением шага (а не при постановке в очередь). Rclone получает положительные правила для нужных веток и завершающее исключение всего остального. Исходные исключения стоят раньше разрешающих правил. Неполный первый день также включается; возрастные фильтры остаются точными по mtime.

Периодический полный обход снимает только ограничение каталогов; по явному выбору пользователя также снимаются `min-age`/`max-age`. Он выполняется на очередном запуске после истечения интервала. Первая выборочная попытка начинает отсчёт, успешный реальный полный обход обновляет его; ошибки и dry-run не продлевают интервал. Состояние сохраняется в `kv_state` с отпечатком задачи и настроек. Retention не затрагивается.

Фактическая команда с фильтрами сохраняется в истории шага. Поле `progress.directory_scan` и событие `directory_scan_started` содержат режим (`window`/`full`) и список масок каталогов. Если корни уже поставленного в очередь шага отличаются от актуальной конфигурации, запуск безопасно завершается ошибкой вместо обхода другого дерева.

## 🧹 Периодическая очистка и окно истёкших дат

Retention шаг остаётся в истории каждого запуска, но проверяет актуальные настройки **перед выполнением**. До срока очистки или после неудачного копирования он завершается `skipped`, без ошибки запуска. `interval_enabled=false` сохраняет режим после каждого успешного копирования.

`retention.directory_scan` создаёт разрешающие маски для недавно истёкших календарных дат, а не для свежего окна копирования. Диапазон: начало последней успешной очистки минус `min_age` и `overlap_days` до текущего времени минус `min_age`, включая пограничный день. Сначала применяются исходные исключения, затем даты и завершающее исключение остальных веток. `--min-age` не снимается ни в одном режиме. Отдельный полный контрольный обход проверяет старые/вне-масочные ветки; неизвестная история и слишком большой разрыв также требуют полного обхода.

Состояние `retention_policy:<job>:<fingerprint>` хранит `last_success_at`, `last_cleanup_started_at`, `last_full_scan_at`. Для периода используется время завершения, для границы возраста — время начала. При активации можно принять существующий успешный нефильтрованный retention с той же командой отбора, без dry-run. Успешный реальный запуск обновляет состояние внутри per-job file-lock до его освобождения; ошибки, остановки, пропуски и dry-run не двигают отсчёт. Перезапуск сервиса сохраняет состояние. Изменение периода не создаёт нового отпечатка.

Фактические фильтры записываются в команду шага. `progress.retention_policy` и событие `retention_policy_selected` содержат режим, причины пропуска и следующий срок. `active_operations` отдельно показывает фазу очистки, завершённость копирования и счётчики `listed_count`/`deleted_count`, не включая очистку в скорость копирования. `backup_jobs[].retention_status` описывает сроки очистки.
