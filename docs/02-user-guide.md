## 🏗️ Архитектура

Проект устроен так:

- приложение принимает команды из UI, scheduler и встроенного watcher
- `rclone` выполняет копирование и синхронизацию
- очереди распределяют запуск задач по профилям
- SQLite хранит историю и текущее состояние

### Основные компоненты

| Компонент | Назначение |
| --- | --- |
| FastAPI app | API, dashboard и операции управления |
| Scheduler | Плановые запуски по расписанию |
| Workers | Исполнение задач из очередей |
| Watcher | Наблюдение за каталогами и запуск задач по событиям |
| SQLite | История запусков, шагов, событий и состояние scheduler |

### Поток выполнения

1. Запуск создаётся из dashboard, API, scheduler или watcher.
2. Профиль попадает в нужную очередь.
3. Worker берёт актуальные задачи из рабочего каталога.
4. Каждый шаг выполняет `rclone` или shell-команду.
5. Результаты сохраняются в SQLite и сразу становятся доступны в UI и API.

## 🚀 Usage

После запуска доступны:

- dashboard: `http://<host>:8080/`
- проверка сервиса: `GET /api/health`
- лёгкий снимок для Homepage: `GET /api/homepage`
- текущее состояние: `GET /api/state`

### Базовый сценарий работы

1. Поднять приложение через `docker` или `systemd`.
2. Открыть dashboard.
3. Проверить состояние очередей, scheduler и последних запусков.
4. Запустить профиль или отдельную задачу вручную.
5. Просмотреть историю запусков и результат шагов.

### Профили по умолчанию

| Профиль | Назначение |
| --- | --- |
| `standard` | Частые и короткие задачи |
| `heavy` | Долгие и ресурсоёмкие задачи |
| `all` | Сводный запуск всех очередей из UI |

Набор очередей можно менять в настройках. В шаблоне каталога по умолчанию уже есть `standard` и `heavy`.

- принудительное включение step-лога `rclone` для отдельной backup-задачи
- исключения через `exclude patterns` с масками `rclone`, например `*.tmp`, `vzdump-qemu-400*`, `**/cache/**`
- исключения по путям через `exclude_paths`: выбор одного или нескольких файлов/каталогов внутри исходного каталога
- `Mail.ru safe preset` для бережного режима `rclone`
- расписание
- таймауты
- retention-политику
- уведомления Gotify
- параметры очередей
- глобальный лимит скорости
- включение подробного `rclone`-лога
- автоматическое включение `rclone`-логов по порогу ошибок
- принудительный step-лог для отдельных backup- и command-задач, если command начинается с `rclone`
- глобальное включение watcher и debounce
- включение watcher у отдельных backup-задач
- фильтрацию watcher-событий через `exclude patterns` и `exclude_paths`
- сериализацию запусков для Mail.ru remote на вкладке `Облака`
- размер SQLite-базы на главной панели статуса
- диагностику и профилактику SQLite в разделе `Статистика`

### Обход каталогов по датам

В редакторе задачи есть отдельный блок **«Обход каталогов по датам»**. Он подходит для обычного `copy`, когда дата записи отражена в пути каталога (например, Frigate). Для `sync`, команд и архивирования режим недоступен.

Настройки:

- включение выборочного обхода;
- относительная маска пути: `%Y-%m-%d`, `%Y/%m/%d`, `cameras/*/%Y-%m-%d` (обязательны год `%Y`, месяц `%m`, день `%d`; `*` — glob внутри одного компонента);
- окно дат в днях и часовой пояс UTC/IANA;
- включение периодического полного обхода и интервал в часах;
- отдельный переключатель игнорирования `min-age`/`max-age` **только при полном обходе**.

Обычный запуск обходит только соответствующие даты, включая неполный первый день. Исходные исключения и возрастные фильтры файлов продолжают работать. Каталоги вне маски пропускаются: для поздно появившихся файлов в старых папках нужна полная сверка. Для Frigate с папками в UTC используйте UTC независимо от часового пояса GUI.

Полный обход выполняется при ближайшем обычном запуске после истечения интервала, не отдельным таймером. Первый запуск выборочный и начинает отсчёт; успешный полный обход переносит следующую сверку. Ошибка или dry-run не считаются успешной сверкой. Отсчёт хранится в SQLite, переживает рестарт и начинается заново при изменении настроек выбора/источника/назначения/опций.

По умолчанию полный обход сохраняет возрастные фильтры: он найдёт недавно изменённые файлы и вне выбранных каталогов. Если нужно проверять также старые неизменённые файлы, включите игнорирование возраста. Это может загрузить большой архив; retention при этом **не изменяется** и может затем удалить слишком старые файлы из облака.

На выборочных запусках `fast_list` отключается, чтобы не обходить исключённые ветки. Дополнительные аргументы отбора/удаления, конфликтующие с выбором дат, отклоняются при сохранении. Retention и встроенный watcher не ограничиваются маской: оптимизация касается только шага копирования.

### Периодическая очистка облака

В блоке **«Очистка в облаке»** можно отдельно настроить:

- выполнять очистку после каждого успешного копирования (прежнее поведение) либо не чаще заданного интервала в часах;
- выборочный обход **недавно истёкших дат**, с собственной маской `%Y-%m-%d`/`%Y/%m/%d`/`cameras/*/%Y-%m-%d` и часовым поясом;
- перекрытие предыдущих дат в днях (по умолчанию 1) для повторной проверки пограничных записей;
- период полного контрольного обхода облака в часах (по умолчанию 168), либо его отключение.

Маска может совпадать с копированием, но **выбираемые даты противоположны**. Копирование смотрит свежие каталоги, а очистка — те, чей срок хранения недавно истёк. Граница вычисляется из `min-age`: поддерживаются положительные длительности `s`, `m`, `h`, `d`, `w`, включая `1d12h` и `0.5d`. Неполный пограничный день включается; окончательное решение об удалении всегда принимает rclone по `--min-age`. Исключения сохраняются. `purge` и автоматическое удаление каталогов не используются.

Выборочный запуск проверяет даты от начала последней успешной очистки минус возраст хранения до текущей границы, плюс перекрытие. При долгом перерыве диапазон расширяется: пропущенные даты не теряются. Сроки хранятся в SQLite; ошибки, остановка и dry-run не продлевают интервал. Несколько workers одной задачи не запускают очистку одновременно. После неудачного копирования очистка пропускается.

Если ещё нет подходящей успешной очистки, первый запуск делает полную контрольную очистку. При включении функции можно использовать историю ранее успешного полного обхода с тем же назначением, возрастом и исключениями. Период считается от завершения успешной очистки; граница выбора дат — от её начала, чтобы длительное выполнение не создавало пропусков.

Поздно добавленные файлы в очень старых папках, несоответствие даты папки времени изменения файла и файлы вне маски обнаруживаются при полном контрольном обходе. Если его отключить, перекрытие не гарантирует обработку всего старого архива. Даже полный обход **никогда не снимает `min-age`**. Изменение периода не сбрасывает уже сохранённый отсчёт.

Очистка выполняется при ближайшем обычном запуске после наступления срока, а не отдельным таймером. Ручной запуск задачи тоже соблюдает интервал. Пропуск очистки до срока имеет статус `skipped` с причиной и датой следующей очистки, но не делает успешное копирование ошибочным. В прогрессе отдельно показывается **«Копирование завершено • очистка облака»** и счётчики просмотренных/удалённых элементов вместо фиктивной передачи `0 Б`.

### Статистика и состояние базы

Раздел `Статистика` показывает не только сводку запусков за выбранный период, но и техническое состояние runtime-хранилища:

- общий размер SQLite-файлов
- размер основного `taskboard.db`
- размер WAL-журнала
- объём, который примерно может вернуть `VACUUM`
- режим журнала SQLite
- открытые файловые дескрипторы backend-процесса
- память и uptime процесса

На главной панели остаётся только компактный виджет `База` с текущим размером.
Подробности и профилактические кнопки находятся внутри `Статистика`, чтобы не перегружать основной экран.
Когда раздел открыт, сводка запусков и диагностика базы обновляются автоматически вместе с общим polling dashboard. Кнопка `Обновить всё` нужна для ручного обновления без ожидания следующего тика.

Кнопка `Сбросить WAL` выполняет checkpoint SQLite и освобождает разросшийся WAL-журнал.
Кнопка `Сжать базу` запускает `VACUUM`; её лучше нажимать без активных копирований, потому что SQLite перепаковывает файл базы.

### Homepage/customapi

Для внешнего Homepage лучше использовать лёгкий endpoint `GET /api/homepage`, а не полный `/api/state`.
Он отдаёт только компактные числа для виджетов и не заставляет backend каждый раз собирать историю запусков и полный dashboard-state.
Скорость, открытые запуски и очереди обновляются на каждый запрос, поэтому `refreshInterval: 500` даст почти real-time скорость.
Медленные поля вроде размера БД, WAL и количества задач кэшируются на стороне taskboard на `slow_cache_seconds`, чтобы частый polling не гонял диагностику SQLite без необходимости.

Пример:

```yaml
widget:
  type: customapi
  url: http://100.100.0.243:8080/api/homepage
  refreshInterval: 500
  mappings:
    - field: total_copy_speed_megabits_per_second
      label: Speed
      format: float
      suffix: " Mbps"
    - field: open_runs_total
      label: Open Runs
      format: number
    - field: database_total_size_bytes
      label: DB
      format: bytes
```

Если Homepage опрашивает endpoint чаще, taskboard всё равно обновляет тяжёлую часть снимка не чаще `slow_cache_seconds`.

## ❓ FAQ

### Пройдёт ли чистый запуск без `default_jobs.json`?

Да. При первом запуске приложение создаёт `default_jobs.json` из `default_jobs.example.json`.

### Где задаются параметры доступа к облакам?

Основной источник данных для облаков теперь `rclone.conf`. Интерфейс читает remotes оттуда и не редактирует их напрямую.

### Что выбрать: `docker` или `systemd`?

| Режим | Когда использовать |
| --- | --- |
| `docker` | Если удобнее контейнерный запуск |
| `systemd` | Если нужен запуск напрямую на хосте |

Подробности по установке вынесены в [Deployment](07-deployment.md).

### Что проверять после развертывания?

- `GET /api/health`
- `GET /api/homepage`
- `GET /api/state`
- `GET /api/system`
- создание SQLite database
- создание `default_jobs.json`
- успешный ручной запуск задачи или профиля
